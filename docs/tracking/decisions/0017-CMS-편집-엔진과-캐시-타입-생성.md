# 0017 · CMS 편집 엔진 · 캐시 · 관리 전용 레이아웃 · 타입 생성

## 왜 정해야 했나

명세(페이지·메인·메뉴·SEO·다국어)를 CMS 로 옮기면서 같은 종류의 선택이 여러 번 나왔다.
다르게 갈 수도 있었던 것만 적는다.

## 무엇을 골랐나

1. **페이지 칸 구조(스키마)는 api 가 가진다**(`api/src/core/page/schema`). 관리 화면은 api 가 준 스키마로
   폼을 그리고, 저장 규칙(모르는 칸 거부·길이·그림 존재·richtext 소독)도 api 가 본다. web 의 형은
   스키마에서 생성한다(`web/lib/page-types.gen.ts`). 화면 파일의 기본 글(`content.ts`)은 api 가 안 닿을 때의 예비다.
2. **메뉴는 60초 태그 캐시 + 저장 뒤 비우기, 페이지 글·게시판은 요청마다(no-store).** 머리글은 모든 장에 있어
   no-store 면 전부 동적이 된다. 페이지 글은 저장 즉시 보여야 하고 비용이 작다(로컬 TTFB 중앙값 9~23ms).
   공개 장은 결국 거의 다 동적이다. api 를 다른 장비로 옮기면 TTFB 를 다시 재고 페이지 글도 태그 캐시로 옮길지 본다.
3. **관리 화면은 자기 루트 레이아웃을 가진다** — 공개 장을 `app/(site)/` 경로 묶음으로 옮겼다(주소는 그대로).
   `/admin` 은 공개 사이트의 CSS·jQuery·Swiper·GTM 을 하나도 싣지 않는다.
4. **web 형은 api 에서 생성한다** — `api/scripts/openapi.js`(서버·DB 없이) → `web/scripts/gen-types.mjs`.
   `openapi-typescript` 는 TypeScript 5 컴파일러 API 에 기대고 web 은 TypeScript 7 이라 생성기를 직접 썼다.
   낡으면 `web/scripts/check-types.py` 가 실패한다.
5. **새 표 이름은 Directus 시절 남은 표를 피한다** — `page_contents`(옛 `pages`), `site_menu_items`(옛 `menu_items`),
   `home_banners`·`home_popups`(옛 `popups`·`home_settings`). 옛 표는 건드리지 않았다(지우기는 사용자 결정, graph-state X3).
6. **메인 배너는 슬라이드가 아니라 기간을 정해 머리 그림을 바꿔 끼우는 것**이다. 이전 디자인이 슬라이드를 일부러
   뺐다. 팝업은 한 번에 하나, 서버는 그리지 않는다(JS 끄면 안 뜨고 아무것도 가리지 않는다).

## 안 고른 것

- **web 에 스키마를 두기** — 저장 규칙이 둘로 갈라진다(「프론트를 고려하면서 만든거 맞아? 코드 같이 있는데?」).
- **루트 `shared/` 패키지** — web 이미지가 `./web` 만 보고 빌드한다. 빌드 범위를 바꾸는 대신 생성으로 풀었다.
- **모든 공개 장을 no-store 로** — 머리글 하나 때문에 캐시를 버리게 된다.

## 그래서 생긴 제약

- api DTO·스키마를 바꾸면 `node api/scripts/openapi.js && node web/scripts/gen-types.mjs` 를 돌리고 생성본을 같이 커밋한다.
- `api/openapi.json` 이 저장소에 있다. 배포가 저장소를 웹 루트로 통째로 올리므로 공개 주소로 열린다 —
  api 소스가 이미 그렇게 열려 있어 새로 드러나는 것은 없다.
