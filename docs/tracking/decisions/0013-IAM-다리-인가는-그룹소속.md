# 0013 · CMS IAM 로그인의 인가는 IAM 그룹 소속이다 (게이트웨이 안 거침)

> **대체됨** — [0014](0014-Directus-은퇴-자체-관리화면.md). Directus 와 그 확장은 없어졌다.

## 왜 정해야 했나

IAM 다리 확장의 소스가 사라져 다시 써야 했다. 원래 설계는 IAM 토큰으로
게이트웨이 `root/iam` → `tenant/by-root` 를 거쳐 「이 테넌트의 root 인가」로
인가했다. 그런데 지금 닿는 게이트웨이는 `root/iam` 에 게이트웨이가 넣는
`x-user-*` 헤더를 요구해서 어디서 불러도 403 이다. 그 단계가 필수인 한
로그인이 끝까지 가지 않는다. 가짜 IAM 이 있었던 이유가 이것이다 — PHP 와
무관하다.

## 무엇을 골랐나

- 인가는 **IAM 그룹 소속**이다. IAM 토큰(`@drvalue-oss/iam-core` 의
  `JwtPayload`)이 `groups: [{id, role}]` 를 들고 오므로, `IAM_BRIDGE_GROUP` 에
  drvalue 그룹을 두고 역할이 OWNER/ADMIN 이면 통과 = 「테넌트 root 사용자 전부」.
  `PLATFORM_ADMIN` 은 통과. 게이트웨이를 안 거친다.
- 게이트웨이 확인(`IAM_BRIDGE_ROUTE_BASE`)과 이메일 허용 목록(`IAM_BRIDGE_ACCOUNTS`)은
  대안으로 남긴다. 셋 다 비면 전부 거부한다.
- 통과한 사람은 `IAM_BRIDGE_DEFAULT_ACCOUNT` 한 계정으로 들어온다(seat 3).
- 가짜 IAM 과 `verify-iam-bridge.sh` 를 지운다. IAM 없이 잴 수 있는 것
  (상태·state 위조·쿠키 누출)은 `smoke.sh` 에 넣고, 실제 로그인은 사람이 한다.

## 안 고른 것

- **Nest 를 게이트웨이 동급으로 승격해 `x-user-*` 를 직접 넣는다** — 이
  프로세스가 뚫리면 사내 전 서비스의 사용자 사칭이 된다.
- **`route.drvalue.co.kr` 복구를 기다린다** — 인프라 결정이라 우리 손이 아니다.
  복구되면 `IAM_BRIDGE_ROUTE_BASE` 를 채우는 것으로 3)이 다시 켜진다.

## 그래서 생긴 제약

- 허용 목록의 사람이 사내 권한을 잃어도 목록을 고칠 때까지 들어온다.
- IAM 콜백 주소가 IAM 화이트리스트에 있어야 한다. 로컬 주소가 등록돼
  있는지는 실제로 눌러 봐야 안다.

## 덧붙임 (같은 날) — 로그인은 IAM 만

- 브라우저의 비밀번호 폼을 막는다. `iam-bridge-entry` 훅이 `Origin` 헤더가 있는
  `POST /auth/login` 을 403 으로 돌려보낸다. 브라우저 폼 제출에는 Origin 이 붙고
  curl·python 스크립트에는 안 붙는다 — 그래서 smoke·seed·service_account 는
  그대로 통과한다. 이 검사를 「이상하다」고 지우면 폼이 되살아난다.
- `/admin/login` 은 세션 쿠키가 있어도 IAM 으로 보낸다. 세션이 살아 있는데 그
  주소를 여는 경우는 없고, 죽은 쿠키로 열면 폼이 계속 뜨기 때문이다.
- 복구: IAM 이 죽어 아무도 못 들어가면 `IAM_BRIDGE_ENABLED=false` 로 재기동한다.
  계정 비밀번호는 파생값이라 관리 화면에서 새로 정하려면 스크립트로 바꾼다.
- 그룹은 uuid 로만 맞춘다. 실측 그룹 이름 "Default" 는 어느 워크스페이스에나 있을 이름이다.
