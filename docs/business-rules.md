# 도메인 규칙

이 사이트가 파는 것은 제조 현장용 시스템 구축이다. 화면의 목적은 하나 —
**문의를 받는 것**이다. 판매도 가입도 결제도 없다.

## 절대 깨지면 안 되는 둘

**게시판 글**과 **문의 접수**다. 나머지는 깨져도 고치면 된다.
이 둘이 깨지면 회사가 소식을 못 알리고 고객이 연락할 길이 없다.

## 문의

- 칸은 넷이다: 회사명/성함(`user_name`) · 연락처(`user_tel`) ·
  문의 유형(`user_type`) · 문의 내용(`user_msg`). 넷 다 필수다.
- 길이 한도: 이름 200자 · 연락처 50자 · 내용 5000자.
  **한도를 좁히면 안 된다.** 좁히는 순간, 지금 PHP 로는 들어가던 문의가
  거절되기 시작한다.
- 한 IP 가 분당 5건 · 시간당 30건까지 보낼 수 있다. 넘으면 429 다.
- 문의 유형 값은 아홉이다: 지원사업 · `CutON(레이저 견적)` ·
  `growchat(채팅 솔루션)` · `M.AX(MES·스마트 팩토리)` ·
  `오토폼(한글 양식 자동 작성)` · `GrowTalk(협업 플랫폼)` ·
  `GrowXD(AI 분석 MES)` · 솔루션 도입 문의 · 기타. 새 값은 api 의
  `INQUIRY_TYPES` · 문의 모달 · openapi · `api-types.gen.ts` 네 곳에 같이 넣는다. 첫 칸은 비어 있고
  고를 수 없다(고르기 전에는 제출이 막힌다).
- **접수 성공을 「응답 200」으로 판정하지 않는다.** 저장이 조용히 깨진 적이
  있다 — 없는 필드에 쓰는 바람에 값이 버려졌는데 화면에는 성공이 떴다.
  판정은 「저장소에 행이 생겼고 값이 원문 그대로인가」로 한다.

## 게시판

- 게시판은 종류로 나뉜다. 공개 화면이 쓰는 글 게시판은 **공지사항**·**보도자료**·**뉴스** 셋이다.
- 글의 공개 여부는 상태 값이 정한다. 공개 화면은 **공개 상태만** 읽는다.
  초안·예약 상태의 글은 목록에도 상세에도 나오면 안 된다.
- **고정 글**(`is_pinned`)은 목록 맨 위에 온다.
- **표시 날짜(`published_date`)는 필수다.** 글을 만든 시각이 아니라 사람이
  정한 날짜다. 이 값이 비면 목록의 정렬 기준이 사라진다. 예외는 자동 글 하나 —
  공개한 날(한국 시간)을 적는다(아래 「제조 AI 주간 글」).
- 글 주소는 지금도 `?id=` 지만 값이 번호가 아니라 CMS 의 슬러그다.
  옛 번호(`?id=123`)로 부르면 안 나온다.
- **공개 화면에서는 글을 못 쓴다.** 쓰기·수정·삭제는 관리 화면에서만 한다.
  옛 쓰기 경로는 살아 있으면 안 된다 — 살아 있으면 성공 응답을 받으면서
  사이트에는 안 나오는 글이 생긴다.

## 제조 AI 주간 글 (자동 발행)

주 1회, 제조 AI 소식 한 건을 풀어 쓴 글이 **뉴스** 게시판에 사람 손 없이
올라간다(결정 0020). 「쓰기는 관리 화면에서만」의 하나뿐인 예외다 — 바깥 HTTP
입구는 없고 api 안의 작업이 쓴다. 올라간 글은 관리 화면에서 고치고 내릴 수 있다.

- **사람이 검수하지 않는다.** 자동 검사를 통과한 글만 공개되고, 떨어진 주는
  글이 없다. 떨어진 글은 게시판에 초안으로도 두지 않는다.
- **본문의 숫자는 전부 주장 목록에 있어야 하고**(코드가 문단마다 맞춘다),
  글을 쓴 호출과 다른 호출이 출처 원문을 다시 읽어 주장·문단·날짜를 확인한다.
  「확인」은 모델의 판정이다 — 코드가 보장하는 것은 「숫자마다 주장이 있고,
  그 출처가 실제로 열렸다」까지다. 출처는 발행 14일 안의 것만 쓴다.
- **말투는 지시문에 규칙으로 적혀 있다**(`client/autopost-prompts.ts`). 해외
  자료를 문장째 옮기지 않고 한국어로 새로 쓴다 · 합니다체 · 짧은 문장 ·
  한국어 용어 먼저, 원어는 괄호로 한 번 · 번역투(「~에 의해」, 명사 나열,
  이중 피동) 금지. 국내 기술 블로그 세 곳의 글을 읽고 습관만 옮겼다
  (2026-11-13) — 남의 문장은 지시문에 넣지 않는다(글에 샌다).
- **모델은 둘 중 하나다**: Claude API, 또는 ChatGPT 웹 화면(사람 기계의
  브라우저를 조작한다). 어느 쪽이든 지시문·검사·판정 기준은 같다. ChatGPT
  웹 길에서는 출처 원문을 코드가 직접 열어 판정에 붙인다.
- 수량을 한글로 풀어 쓴 글(「절반」「두 배」「수백억」)은 떨어진다 — 숫자
  검사를 비켜 가는 길이다.
- **회사·제품에 대한 문장을 모델이 쓰지 않는다.** 「디알밸류」·`GrowXD`·
  `CosmoGMP`·`M.AX` 가 모델이 쓴 칸에 나오면 떨어진다(정부의 「M.AX
  얼라이언스」만 통과).
- AI 가 썼다는 표기는 넣지 않는다(사용자 결정 2026-11-12). 이모지도 없다.
- **그림은 ChatGPT 웹 길에서만 붙는다**(2026-11-13). 검사를 통과한 글에
  표지 한 장(본문 맨 위 — 뉴스 게시판은 본문의 첫 그림이 대표 이미지다)과
  단락 그림(단락이 넷이면 2·4번, 셋이면 3번 단락의 제목 아래)을 만든다.
  지시문(일러스트 · 글자·로고·상표·실존 인물 없음)은 코드에 적힌 글자다.
  그림답지 않은 것(가로 800 미만 · 2MB 초과)은 빼고, 표지가 없으면 글은
  그림 없이 나간다. Claude API 길에는 그림이 없다.
- **글의 모양은 코드가 정한다**(2026-11-13 목업 승인 — 잘 읽히는 글 다섯 곳의
  습관을 봤다: 굵은 글씨는 드물고 결론에만 쓰며, 본문 앞에 요약 묶음을 둔다).
  모델은 글자만 쓴다. 위에서부터 —
  - 표지 그림 → **큰 숫자 줄**(`figures` 2~3개, 내세울 숫자가 없으면 없다) →
    옅은 회색 면의 「3줄 요약」(`key_points`).
  - 단락마다 빨강 번호(01·02…) · 제목 · 굵은 결론 한 문장(첫 문단, 90자 이내) ·
    단락 그림 · 문단. 번호 단락은 3~4개, 결론을 받치지 않는 배경은 뺀다.
  - 큰 숫자도 본문 숫자와 같은 검사를 받는다 — 「이름 값」(「생산성 향상 30.1%」)이
    주장 목록에 있어야 하고 판정이 출처와 대조한다.
- **글 끝은 고정 문구다**: 어두운 띠에 「AX 도입을 고민 중이시라면?」 · 「우리
  공장에는 무엇부터 맞을지, 현장 이야기를 듣고 함께 정리해 드립니다.」 ·
  「문의 남기기」 단추(`autopost-render.ts` 의 `CTA_HTML`). 제품 성능·고객사·
  수치를 넣지 않는다. 글 화면 맨 아래의 공용 문의 띠와 겹친다(둘 다 나간다).
- **글의 목적**(2026-11-13 사용자): 읽은 사람이 「우리 공장도 할 수 있겠다」고
  느끼고, 그 근거가 되는 지식을 하나 얻어 가는 것. 그 회사가 어디서부터
  어떻게 시작했는지를 보여 주고, 마지막 단락은 「우리 공장이라면」으로 닫는다
  (끝 문단은 독자에게 던지는 물음 — 사실 주장이 없어 판정이 통과시킨다).
- **누가 쓰나**(2026-11-13 사용자): 글은 Claude 가 쓴다(예약 실행이 깨운
  에이전트가 `--rules` 를 읽고 써서 `--article` 로 넣는다). ChatGPT 웹은
  사실 대조(판정)와 그림만 맡는다 — 쓴 쪽과 대조하는 쪽이 다른 모델이다.
  ChatGPT 가 조사·집필까지 하는 길도 남아 있다.
- **공개는 묶음으로 한다**(2026-11-13): 맥에서 검사·판정·그림까지 끝낸 글을
  한 파일로 묶고, DB 가 있는 곳에서 `--publish-bundle` 로 연다. 한 주에 한 편,
  이미 낸 출처는 다시 못 쓴다(주간 기록). 사람 검수는 여전히 없다.
- **그림의 내용은 다른 모델이 본다**(2026-11-13 사용자: 「하네스 해줘」). 받은 그림을
  Codex CLI 가 직접 보고 글자·로고가 있는 그림과 같은 장면이 겹친 뒤 그림을
  뺀다. 판정하지 못하면(도구 없음·실패·답이 모자람) 그림 없이 간다 — 판정
  불가는 통과가 아니다. 표지가 빠지면 그림 전부가 빠진다.
- **그림은 자리마다 장면이 다르다**: 표지는 현장 전경, 가운데 단락은 사람 없는
  근접, 마지막 단락은 현장 사람들. 그림은 마지막 단락과(단락이 넷이면) 둘째
  단락에 넣는다.
- **읽는 사람은 개발자가 아니다**(2026-11-13 사용자 요청): 공장 대표·공장장·
  생산관리 담당이 한 번 읽고 옆 사람에게 전할 수 있게 쓴다. AI 모델·제품
  이름은 꼭 필요한 하나만 한 번, 개발 용어(모델·추론·벤치마크·PoC)는 현장
  말로 바꾸거나 뺀다. 「~은 아닙니다」 같은 단서는 글 전체에서 한 번만.
  지시문의 규칙이고 코드 검사는 없다.
- **주제는 둘이다**: ① 해외 도입 사례, ② 공장에 들이면 좋을 새 기술·기법
  (현장에서 써 본 결과가 같이 나온 것만). 둘 다 있으면 ①.
- **주제는 해외 현장 사례가 먼저다**(2026-11-13 사용자 요청): 「해외 어느 회사가
  공장에 AI 를 이렇게 들였다더라」고 전할 수 있는 제조 AX 소식. 14일 안에
  없을 때만 국내 사례, 그다음 정책 소식. 행사·협약·수상 소식은 고르지 않는다.
- **검사가 못 막는 것**: 그림 판정의 오판(글자·로고·겹친 장면은 다른 모델이 보지만 그 판정이 틀릴 수 있고, 그림이 글의 내용과 맞는지·실존 인물을 닮았는지는 아무도 안 본다) · 일반 용어 풀이·비유가 맞는지(판정은 「출처와 어긋나지
  않으면 통과」로 본다 — 출처에 없는 설명이라 대조할 원문이 없다) · 출처 자체가 틀렸거나 과장된 경우 · 수치는 맞는데
  해석이 과한 문장 · 판정 호출의 오판(숫자 없는 인용·발표·계약 문장은 판정
  호출만 본다) · 목록에 없는 방식으로 회사·제품을 가리키는 말 · 중요하지
  않은 소식을 고르는 것.

## 보도자료의 「보도일」과 「올린 날」은 다르다

언론 기사가 나간 날과 우리가 그것을 사이트에 올린 날은 같지 않다.
표시하는 것은 **보도일**이다. 올린 날을 보도일로 적으면 하루 이틀 어긋나고,
읽는 사람은 그 차이를 알아챈다.

## 화면에 적는 숫자

특허·저작권·수행실적 건수처럼 화면에 적는 숫자는 **세는 근거가 화면 안에
있어야 한다.** 예를 들어 「수행실적 9건」의 근거는 같은 장의 표 9줄이다.
근거 없는 숫자는 적지 않는다.

세는 대상이 여러 자리에 나오면 **한 곳에서 세어 나눠 쓴다.** 손으로 적어
두면 자료가 늘었을 때 한쪽만 고쳐진다. 실제로 「제조 AI 기능 5가지」라고
적어 놓고 눌러 보면 셋만 있던 적이 있다 — 세는 자리가 「가진 목록」을 세고
장은 「싣는 목록」을 그렸기 때문이다.

## 화면에 쓰는 글은 지어내지 않는다

제품 설명·기능 이름·과제명은 전부 **실제로 가진 자료**에서 온다. 회사가
확인해 주지 않은 성능 수치나 고객사 이름을 화면에 쓰지 않는다. 자료가
없으면 그 칸을 비우거나 구역을 통째로 안 그린다 — 빈 상자를 띄우지 않는다.
